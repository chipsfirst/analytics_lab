# Ревью проекта

## Чек-лист

- [ ] У каждой модели явное зерно.
- [ ] Join не размножает строки; проверено `unique` или ручным count.
- [ ] NULL обработаны: `not_null`, `nullif`, осознанные пропуски.
- [ ] Даты приведены к одному типу и часовому поясу.
- [ ] Дубли платежей удалены до агрегации.
- [ ] Статусы и тарифы ограничены `accepted_values`.
- [ ] Ссылочная целостность проверена `relationships`.
- [ ] Метрики в BI совпадают с SQL из `dashboard/kpi.sql`.
- [ ] Нет `select *` в marts без причины.
- [ ] Есть README, владелец и ограничения.

## Пример PR и разбор

```sql
select p.*, u.channel
from stg_payments p
left join stg_users u using (user_id)
where p.status = 'paid'
```

Что сказать на ревью:

1. **Зерно не задано.** Непонятно, одна строка — платёж, пользователь или день. Нужен `payment_id` и проверка уникальности.
2. **`select *`.** Схема поедет при добавлении колонки; для витрины перечислите поля явно.
3. **`left join` + фильтр по правой таблице.** Фактически превращается в inner join; если нужны все платежи, фильтр надо перенести.
4. **Возвраты потеряны.** `status = 'paid'` исключает refunded; для net revenue нужен отдельный расчёт.
5. **Нет тестов.** Добавьте `unique`/`not_null` на ключ и `relationships` на пользователя.
6. **Нет периода.** Непонятно, за какой месяц и на какую дату считается метрика.

## Как писать ревью

- Сначала факт: «в `fct_payments` 15 дублей по `payment_id`».
- Потом риск: «выручка завышается при join».
- Потом действие: «дедуплицируйте в staging и добавьте тест `unique`».
- Не переходите на личность и не говорите «плохо» без примера.
